# 🪐 Комплексное исследование SIEM Wazuh против утилит сетевого штурма Nmap

## 🏗️ 1. Архитектура и Спецификация Лабораторного Полигона

Для проведения эксперимента была развернута инфраструктура, состоящая из трех операционных систем, изолированных в виртуальной сети Host-Only под управлением гипервизора:

1. **Сервер Мониторинга (Blue Team Server):**
   * **ОС:** Ubuntu Server 24.04 LTS
   * **Компоненты:** Wazuh-Manager (Центральный сервер сбора и анализа логов, индексатор событий).
   * **Сетевая конфигурация:** Статический IP в подсети лаборатории.
2. **Хост Мониторинга (Target Host):**
   * **ОС:** Windows 10 (Хостовая машина с развернутыми агентами защиты).
   * **Компоненты:** Wazuh-Agent v4.x, Microsoft Sysinternals Sysmon v15.21.
3. **Платформа Атаки (Red Team Enterprise):**
   * **ОС:** Kali Linux (Специализированный дистрибутив для проведения тестирования на проникновение).
   * **Инструментарий:** Nmap v7.99, встроенные скрипты автоматизации NSE (Nmap Scripting Engine).

## 🕳️ 2. Раунд №1: Слепое сканирование (Дефолтная конфигурация)

### Цель этапа:
Проверить эффективность стандартных механизмов мониторинга Wazuh-agent против классической сетевой разведки злоумышленника.

### Симуляция атаки (Kali Linux):
С атакующей платформы было запущено агрессивное сканирование с определением версий служб, операционной системы и запуском стандартных скриптов:

```bash
sudo nmap -A 192.168.3.46
```

### Анализ поведения систем:
* **Со стороны Kali Linux:** Сканер успешно вернул список открытых портов хоста Windows.
* **Со стороны Wazuh Dashboard:** На графиках `Security Events` зафиксировано **0 событий**. Полная слепота.

!

### Технический вывод:
Стандартный агент Wazuh для Windows ориентирован на мониторинг классических системных журналов (Application, System, Security). Он физически не перехватывает трафик на сетевом уровне, если входящие соединения не приводят к критическим ошибкам служб или созданию деструктивных процессов. Проводя пассивную или активную разведку, хакер остается полностью невидимым.

## 🛡️ 3. Раунд №2: Активация Локального Аудита ОС и Борьба с Локализацией

### Задача:
Настроить фиксацию угроз типа "Внутренний нарушитель" и преодолеть капризное поведение утилиты `AuditPol` в русскоязычной Windows.

### Проблема языкового барьера:
Попытка включить аудит через стандартные англоязычные подкатегории привела к системной ошибке `0x00000057 (Параметр задан неверно)`:
```powershell
# Ошибка: Windows не распознает англоязычные сущности в русской локализации
auditpol /set /subcategory:"Logon" /success:enable /failure:enable
```

### Инженерное решение (Обход через GUID):
Чтобы сделать скрипт универсальным для любой Windows в мире (вне зависимости от языка интерфейса), была применена техническая хитрость — принудительное включение категорий через их **скрытые системные GUID**:
```powershell
# Включение аудита категории "Вход/Выход" для всех подкатегорий разом на глобальном уровне
auditpol /set /category:"{69979849-797A-11D9-BED3-505054503030}" /success:enable /failure:enable
```

### Симуляция внутренних атак:
1. **Локальный брутфорс:** Симуляция перебора паролей через цикличный вызов системной утилиты:
   ```powershell
   1..10 | ForEach-Object { net user Administrator НеверныйПароль123! }
   ```
2. **Стирание улик (Anti-forensics):** Попытка злоумышленника очистить журнал безопасности, чтобы скрыть следы пребывания:
   ```powershell
   wevtutil cl Security
   ```

### Результат в Wazuh Dashboard:
Общий счетчик событий зафиксировал мощный всплеск (**900+ событий**). Система успешно вывела на главный экран критический алерт **Authentication failure** и зафиксировала изменение политик безопасности (`policy_changed`).

## 📡 4. Раунд №3: Создание Сетевого Радара на базе Sysmon

### Задача:
Заставить Windows видеть сетевые налеты Nmap и передавать эти данные в SIEM.

### Модификация ядра Sysmon (Борьба с фильтрами):
Дефолтный конфигурационный файл от *SwiftOnSecurity* полностью блокировал логирование сети (`NetworkConnect`), чтобы избежать перегрузки процессора. Попытка очистить теги "в лоб" приводила к тому, что драйвер Sysmon v15+ полностью отключал сетевой модуль из-за отсутствия правил.

В Блокноте структура XML-манифеста `sysmonconfig-export.xml` была приведена к строгому кастомному виду, включающему мониторинг только критических портов (выровнена вложенность тегов):
```xml
<RuleGroup name="" groupRelation="or">
  <NetworkConnect onmatch="include">
    <DestinationPort condition="is">445</DestinationPort>
    <DestinationPort condition="is">22</DestinationPort>
    <DestinationPort condition="is">3389</DestinationPort>
  </NetworkConnect>
</RuleGroup>
```
*Конфигурация успешно применена в PowerShell командой `.\sysmon64.exe -c sysmonconfig-export.xml`.*

### Сетевой штурм (Kali Linux):
На хосте Windows временно деактивирован брандмауэр (`Set-NetFirewallProfile -Enabled False`). С Kali запущен тяжелый скриптовый налет уязвимостей и перебора на SMB-порт (445):
```bash
sudo nmap -sV --script default,discovery,vuln -p 445 192.168.3.46
```

## 🧠 5. Великий Парадокс Логирования и Архитектурный Фикс `ossec.conf`

### Проблема "Мёртвой панели":
Несмотря на то, что Nmap выдал огромный отчет, а локальный *Просмотр событий Windows* (`Event Viewer`) ломился от записей **Event ID 3 (Network connection detected)**, панель Wazuh Dashboard изначально показывала **0 результатов** по поиску атакующего IP `192.168.3.50`.

### Анализ и расследование причин:
В ходе глубокого анализа была вскрыта фундаментальная архитектурная ошибка конфигурации агента. Стандартный формат сбора логов `eventlog` в `ossec.conf` не способен считывать данные из современных глубоких журналов приложений Windows (`Applications and Services Logs`), где и обитает Sysmon. Агент читал только логи входа в систему, полностью игнорируя сеть.

### Финальный Архитектурный Фикс:
В конфигурационном файле агента `C:\Program Files (x86)\ossec-agent\ossec.conf` формат логирования был принудительно переведен на современный интерфейс каналов Windows — **`eventchannel`**:
```xml
<localfile>
  <location>Microsoft-Windows-Sysmon/Operational</location>
  <log_format>eventchannel</log_format>
</localfile>
```
*После применения фикса служба была перезапущена: `Restart-Service -Name "Wazuh"`.*

## 🏆 6. Триумф Лабораторной Работы и Структура Пойманного Инцидента

Перевод на `eventchannel` мгновенно пробил засор в передаче данных. Wazuh Dashboard вывалил лавину сырых структурированных логов. Из недр SIEM во вкладке *Events* был успешно извлечен паспорт пойманной атаки Nmap:

```json
{
  "win.eventdata.sourceIp": "192.168.3.50",
  "win.eventdata.destinationPort": "445",
  "win.eventdata.initiated": "false",
  "win.eventdata.image": "System",
  "win.eventdata.parentCommandLine": "net user guest",
  "win.eventdata.hashes": "MD5=97LF4BCB... SHA256=DBAA0631..."
}
```
*Анализ JSON-лога четко показал, что скрипт Nmap пытался удаленно проверить и скомпрометировать учетную запись `guest` через легитимный системный процесс `net.exe`.*

## 📈 Итоговые Выводы Исследования

1. **Временной Парадокс (UTC vs Local):** В ходе работы была выявлена критическая важность понимания разницы часовых поясов. Записи в журналах Windows и системных логах могут использовать формат UTC, из-за чего динамические фильтры SIEM-системы требуют внимательного контроля временных интервалов.
2. **Агрегация и защита от флуда:** Экспериментально доказано на примере локального брутфорса, что Wazuh не создает алерты на каждую отдельную попытку. Система автоматически объединяет цикличные атаки в единый инцидент высокой важности, защищая панель от флуда.
3. **Главная Истина SecOps:** Безопасность из коробки — это миф. Ни одна современная SIEM-система не увидит целевую сетевую разведку хакера, пока инженер защиты вручную не настроит конфигурацию сбора телеметрии на конечных хостах.
